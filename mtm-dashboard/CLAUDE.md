# MtM Dashboard — 작업 규칙

개인 트레이딩 리스크관리 대시보드. 아키텍처·파일 구조·명령어는 `README.md` 참고.
여기 있는 건 **틀리면 숫자가 조용히 왜곡되는 규칙들** — 이전 세션에서 실제로 틀렸던 것들이다.

## 추적 범위

계좌 3개만: **국장**(삼성증권 7089239210-01) · **ISA**(삼성증권 7156461048-14) ·
**미장**(나무증권 209-01-920722). 삼성증권 CMA/IRP/DC 등 나머지 계좌는 범위 밖 —
자료가 섞여 들어와도 반영하지 않는다. 중국·업비트 계좌는 순자산 추적 대상이 아니고
`cashflow.csv`에서 자금 이동 출발/도착지로만 등장한다.

## 순자산 계산 — 반드시 GROSS/NET 구분

`equity(순자산) = 총평가금액(GROSS, 주식+예수금) - credit(신용대출)`

브로커 리포트의 "총평가"가 이미 신용 차감된 NET인지, 차감 전 GROSS인지 매번 확인할 것.
2026-08 세션에서 이걸 착각해 국장 순자산이 실제의 약 2배로 잘못 들어간 적 있다.
GROSS는 `국장_total`, NET은 `국장_equity` 칼럼에 분리해서 저장한다.

## 신용(credit) 값 — 출처가 정확도를 좌우한다

**신용값은 반드시 앱의 "신용융자금" 탭에서 직접 읽은 값을 쓴다.** 월말잔고 PDF의 "대출"
컬럼이나, 사용자가 요약 형태로 기억을 더듬어 재구성한 파일은 신뢰도가 낮을 수 있다 —
2026-08 세션에서 월별 요약 파일 기준 신용값이 신용융자금 탭 실측치와 최대 30%까지
벌어진 사례를 확인했다(신용대주 때문이 아니라 단순히 요약 자료의 정밀도 문제였음).
사용자가 신용융자금 탭을 직접 보고 확정해준 값은 그대로 신뢰하고 덮어쓴다.

## 데이터 우선순위

1. 사용자가 앱 화면을 보며 직접 옮긴 수기값 (가장 신뢰도 높음 — 라이브 `collect.py` 실측치보다도 우선)
2. PDF/문서에서 뽑아 파생 계산한 값
3. 근거 없는 추정값은 절대 채우지 않는다 — 모르면 공란. "원금이 조용히 틀리면 안 된다."

라이브 실측과 사용자 수기값(평가손익추이 화면 기준)은 D+2 예수금 인정 여부 차이로
며칠간 1~5%대 갭이 날 수 있다 — 정상 범위, 조치 불필요.

## 날짜 규칙

월말이 주말인 스냅샷(예: 2026-01-31 토)은 **직전 금요일 날짜로 이동**해서 저장한다.
거래 없는 주말의 계좌 상태는 직전 거래일과 동일하다는 원칙.

## cashflow.csv 항목 분류

- **원금(principal) 이동으로 취급**: 개시잔액 · 외부입금 · 외부출금 · 계좌간이체
- **원금 이동 아님, 별도 누계로만 집계**: 신용이자 · 강의구독비 · 수수료 · 매도세금 · 배당금
  → `collect.py`의 `load_cashflow_totals()`가 principal 계산에서 제외하고
  `cum_interest`/`cum_course_fees`/`cum_trade_fees`/`cum_sec_tax`/`cum_dividend`로 따로 합산한다.
  (이미 계좌 잔고 변동에 반영된 비용·수익을 원금에서도 빼면 손익이 이중으로 왜곡된다.)
- 신용이자·수수료·매도세금·배당금은 사용자 요청으로 **월말 값만** 입력한다 (일별 아님).
- **신용이자의 실제 반영일은 월말이 아니라 다음달 1일**이다. `cashflow.csv`엔 관행대로
  월말 날짜(예: 2026-08-31)로 기록하지만, 실제 계좌 평가손익(daily.csv의 surface_pnl 등)에
  마이너스로 찍히는 시점은 **그 다음달 1일자**다 (예: 2026-08분 신용이자 3,677,079원은
  2026-09-01 평가손익에 반영됨). 별도로 예수금을 손으로 차감할 필요는 없다 —
  데이터 우선순위 규칙(수기값 최우선)대로 9/1에 사용자가 앱에서 확인한 실측 예수금을
  그대로 넣으면 이미 이자가 빠진 값이라 자동으로 반영된다. daily.csv를 채울 때
  월초 첫날 평가손익이 갑자기 떨어져도 매매손실로 오인하지 말 것 — 신용이자
  차감분인지부터 확인.

## 신용주식 매도 시 예수금은 반드시 직접 확인 — 역산 금지

신용(대주)으로 보유한 종목을 매도하면 매도대금 중 일부가 신용 상환에 먼저
쓰이고 나머지만 예수금으로 들어오는 등, 정산 구조가 계좌마다/케이스마다 달라서
"매도수량 × 매도단가"로 예수금 변동분을 역산하면 틀린다 — 2026-08-31
삼성전기(신용) 5주 매도 때 역산치(2,443,932)와 실제 예수금 사이에 오차가 나서
다음날 전일비가 어긋난 사례가 있었다. **신용 종목 매도가 있었다는 말을 들으면
그 계좌의 결과 예수금이 얼마인지 반드시 사용자에게 물어보고, 앱 화면에서
직접 확인한 값만 `CASH_*`에 채운다** — 매매대금으로 계산해서 채우지 않는다.
(신용 없는 일반 매수·매도는 기존처럼 매매대금 역산도 허용된다 — 정산 구조가
단순해서 오차가 잘 안 남.)

## NXT(대체거래소, 연장거래) 체결 — 익일 반영, 당일 발행에는 미반영

국장 손익은 **정규장 기준**으로 산출한다. 정규장 마감 후 NXT(연장거래)로 체결된
거래는 참고 정보로만 받아두고, 그 다음 거래일(익일) 포지션에 반영한다 — 체결일
자체의 `daily.csv`/대시보드에는 넣지 않는다. 사용자가 NXT 체결 내역을 알려줘도
"이건 익일 반영용으로 메모만 해두고, 오늘자 대시보드는 정규장 기준으로 발행"
하는 게 기본 동작이다. 확정 여부가 불투명하면(사용자가 "아직 확정 안 됐다"고
하면) 포지션에도 손대지 않고 대기한다 — 나중에 확정되면 그때 반영.

## 앱 "매매손익(종목별)" 화면으로 당일 매매 반영하기

증권사 앱의 매매손익 → 종목별 → **원화** 탭 캡처를 주면, 종목마다 2행으로 나온다:
1행 = 매도평균단가 · 매도수량, 2행 = 매수평균단가 · 매수수량 (매도만 있거나 매수만
있으면 한 행만 있음). 이 화면은 "그날 실현손익"용이라 최종 잔여 수량은 안 보여준다 —
직전 `positions.csv` 값에서 다음과 같이 역산한다:

```
잔여수량 = 기존qty − 매도수량 + 매수수량
새 평단  = ((기존qty − 매도수량) × 기존평단 + 매수수량 × 매수평균단가) / 잔여수량
```

매도는 남은 수량의 평단을 바꾸지 않는다(이동평균 방식) — 매도평균단가 자체는 그냥
그날 실현손익 계산에만 쓰이고 포지션 갱신에는 안 들어간다. 매수만 새 평단에 섞인다.
전량매도 종목(캡처에 있지만 "놔둬"라고 확인된 경우)은 `positions.csv`에 원래 없었으면
추가하지 않는다.

## 야후 소급 종가 vs 앱 정규장 종가 — 작은 갭은 있을 수 있다

`collect.py --backfill-prices`로 채운 과거 종가(야후)가 브로커 앱이 보여주는 정규장
종가와 0.5~1.5%대로 다를 때가 있다(연장거래 반영 시점 차이 등 데이터 제공처 차이로 추정,
근본 원인까지 규명하지는 않음). **사용자가 앱 화면에서 직접 확인해준 종가는 그 값으로
덮어쓰고 `source`를 `user(정규장종가 확인)`로 표시한다** — 데이터 우선순위 규칙(수기값
최우선)과 동일하게 취급.

## daily.csv의 `source` 컬럼

- `cache` = `collect.py` 라이브 실행 결과
- `backfill(...)` = PDF·문서 기반으로 역산/추정한 과거값
- `user(수기 키인·...)` = 사용자가 직접 입력해 병합한 실측값 — 가장 신뢰도 높음

### 세션-브랜치 정리 규칙 (2026-08-25 추가)

Claude Code 웹/앱은 새 세션을 열 때마다 `claude/<주제>-<랜덤6자리>` 브랜치를 자동 생성한다
(레포 설정이 아니라 플랫폼 기본 동작 — 이 CLAUDE.md로 끌 수 없음). 세션이 여러 개 동시에
main에 직접 push하다 충돌 나는 걸 막기 위한 장치이므로 완전히 없애지는 말고, 대신 브랜치가
계속 쌓이는 걸 아래 습관으로 관리한다:

- 세션이 작업을 끝내고(review_ready) main에 반영할 준비가 되면, **그 자리에서 바로
  main으로 merge하고 작업 브랜치는 지운다.** "나중에 한꺼번에 정리"로 미루지 않는다.
- 브랜치를 지우기 전 반드시 `git rev-list --left-right --count origin/main...origin/<branch>`
  로 main 대비 고유 커밋이 0인지 확인한다 (merge 완료 확인). 0이 아니면 아직 지우면 안 됨.
- **연결된 세션이 사용자 답을 기다리는 중(status: need_input/blocked)이거나, 세션이 아직
  살아있는(connected) 브랜치는 고유 커밋이 있는 한 지우지 않는다** — 그 세션의 미완료
  작업이 날아간다.
- 사용자가 로컬 Mac 등에서 직접 push한 브랜치(커밋 author가 `Claude`가 아닌 경우, 예:
  `price-history-data`)는 Claude 세션 소유가 아니므로 절대 임의로 지우거나 merge하지 않는다
  — 사용자에게 먼저 확인한다.
- main과 완전히 동일한 내용을 가리키는 낡은 브랜치(예: 예전에 임시 main 대용으로 쓰던
  `claude/google-drive-connector-folders-lu7bxq`)는 지워도 데이터 손실이 없지만, 그 브랜치에
  바인딩된 세션이 아직 살아있다면 굳이 먼저 나서서 지우지 말고 사용자 판단에 맡긴다.

별도의 "백업용 sub 브랜치"(main을 복제해서 따로 유지)는 만들지 않는다 — git 히스토리 자체가
이미 모든 과거 커밋을 영구 보존하므로 실질적 이득이 없고, main이 업데이트될 때마다 수동으로
동기화해줘야 해서 금방 낡은 채로 방치되기 쉽다. 실수로 main 히스토리가 덮이는 사고(옵시디언
건 같은)를 막고 싶으면 GitHub 저장소 설정의 **브랜치 보호 규칙**(force-push 금지, 필수 리뷰
등)을 쓰는 게 낡은 복제 브랜치보다 훨씬 확실하다.

## 대시보드(아티팩트) 반영 절차

**2026-09 갱신: 매크로 차트(`DATA.macro_series`)만 자동화됨.** `collect.yml`이
`collect.py` 실행 직후 `dashboard/build_macro_chart.py`를 이어서 실행해
`data/macro.csv`(미국채10y·WTI·KOSPI·코스닥·NASDAQ·SOX·환율·금 등)를 매일
`risk-console.html`의 `DATA.macro_series`에 자동 주입하고 커밋한다 — 이 부분은
더 이상 수동으로 안 해도 됨. 단, **이렇게 리포에 커밋된 `risk-console.html`이
실제 라이브 Artifact URL로 재배포되는 것은 여전히 수동**이다(Artifact 배포는
Claude Code 세션 안에서만 가능해 GitHub Actions로는 못 함) — 사용자가 "배포해줘"
라고 요청하면 그 시점의 최신 `risk-console.html`을 그대로 Artifact로 재배포한다.

`dash_data.json`(메트릭/시그널/포지션 등 핵심 숫자)과 `DATA.stock_charts`(주가
이동평균선)는 아직 자동화 안 됨 — `daily.csv`/`cashflow.csv`를 고치면 아래 순서를
그대로 수동으로 거친다:

1. rebuild 스크립트로 `dash_data.json` 재생성 (`collect.py`의 `compute()` 등을 재사용)
2. `risk-console.html`의 `const DATA = {...}` 블록에 새 JSON 주입
   (Python 문자열 치환 시 `re.sub`의 문자열 치환 인자는 백슬래시를 이스케이프로 해석하니
   반드시 인덱스 슬라이싱이나 `lambda` 치환을 쓸 것 — 안 그러면 JSON 안의 `\n`이 실제
   줄바꿈으로 깨진다)
3. jsdom으로 로드해 콘솔 에러 0건 확인
4. Playwright로 스크린샷 찍어 시각 확인(라이트+다크 둘 다)
5. 같은 아티팩트 URL로 재배포: `https://claude.ai/code/artifact/66481dfc-fea9-4c7e-8051-5adf12384a77`
6. `git commit`·push (위 Git 규칙대로)

## AI 요약/코멘트 박스 — 배포 시점마다 최신 데이터로 다시 쓸 것

대시보드 안에 사람이 아니라 AI(나)가 문장으로 직접 써 넣는 요약 박스가 3개
있다 — 코드가 계산해서 채우는 다른 필드들과 달리, 이 3개는 매번 그 시점
데이터를 보고 내가 새로 작성해야 하는 자유서술 텍스트다. 재사용 스크립트로
자동 생성되지 않으므로, **자동으로 최신 데이터를 반영하지 않고 배포 시점에
멈춰버린다** — 2026-08-19 시점 내용이 9/3까지 안 바뀐 채 방치된 사례가 있었다.

- `DATA.stock_ai_summary` — View/Index 주가·이동평균선 카드 상단 AI 분석
- `DATA.macro_ai_summary` — View/Index 매크로 지표 카드 상단 AI 분석
- `DATA.view_summary` — Summ./View "이번 주 투자 기조" 상단 AI 요약
  (전문가 패널 카드형, `dashboard/build_view_log.py`로 `DATA.view_log`는
  자동 동기화되지만 `view_summary` 문장 자체는 여전히 수동 작성)

**규칙: "배포해줘" 요청을 받으면, 위 3개 박스를 그 시점 최신 데이터
(`DATA.stock_charts`/`DATA.macro_series`/`DATA.view_log`의 가장 최근
값들)를 근거로 다시 써서 갱신한 뒤에 배포한다.** 내용이 이전과 실질적으로
같더라도(예: 큰 변화가 없는 한 주) 최신 날짜·수치를 반영해 다시 쓴다 — 조용히
stale한 채로 배포하지 않는다. 형식은 기존 톤을 따른다: `<mark>`로 핵심
발견 하이라이트, `<u>`로 실행 가능한 해석/결론 밑줄. 숫자는 반드시 해당
DATA 필드에서 직접 뽑아 쓰고 추정하지 않는다.

운영 가이드 문서(사람이 읽는 버전)는 별도 아티팩트로 관리 중이며 버전이 있다 —
