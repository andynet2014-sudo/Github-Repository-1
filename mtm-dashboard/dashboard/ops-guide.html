01시스템 개요

저장소 andynet2014-sudo/Github-Repository-1(구 260731-, 자동 리다이렉트됨) · 폴더 mtm-dashboard/ · 브랜치 main + claude/google-drive-connector-folders-lu7bxq(항상 두 곳에 동시 push). 핵심 엔진은 collect.py — data/ 아래 csv들을 읽어 리스크 지표를 계산하고 daily.csv에 한 줄씩 기록한다.

추적 대상 계좌는 3개뿐이다: 국장(삼성증권 7089239210-01) · ISA(삼성증권 7156461048-14) · 미장(나무증권 209-01-920722). 삼성증권 CMA/IRP/DC 등 나머지 계좌는 명시적으로 추적 범위 밖. 중국·업비트 계좌는 daily.csv 순자산 추적 대상이 아니고, cashflow.csv에서 자금 이동 출발/도착지로만 등장한다.

02핵심 규칙 · 반드시 지킬 컨벤션

순자산 계산 공식

  • equity(순자산) = 총평가금액(GROSS, 주식+예수금) − credit(신용대출). 브로커 리포트의 "총평가"가 이미 신용 차감된 값인지 GROSS인지 매번 확인할 것 — 2026-08 세션에서 이걸 착각해 국장 순자산이 실제의 약 2배로 잘못 들어간 적 있음(사용자 수기 실측치로 발견·수정).
  • GROSS 값은 국장_total 칼럼에, 신용 차감 후 NET 값은 국장_equity 칼럼에 분리 저장.

데이터 우선순위

  • 사용자 수기 직접 입력 > PDF/문서에서 파생 계산한 값 — 라이브 collect.py 실측치보다도 사용자가 앱 화면에서 직접 옮긴 값을 우선한다.
  • 필수신용(credit) 값은 반드시 앱의 "신용융자금" 탭에서 직접 읽은 값을 쓴다. 월말잔고 PDF의 "대출" 컬럼이나 요약 형태로 재구성한 파일은 신뢰도가 낮을 수 있음 — 2026-08 세션에서 월별 요약 파일 기준 신용값이 실제 신용융자금 탭 값과 최대 30%까지 벌어진 사례를 확인, 신용융자금 탭 실측으로 전량 교체함.
  • 근거 없는 값은 절대 추정해서 채우지 않는다 — 모르면 공란으로 둔다("원금이 조용히 틀리면 안 된다").
  • 월말이 주말인 스냅샷(예: 2026-01-31 토)은 직전 금요일 날짜로 이동해서 저장 — 거래 없는 주말의 계좌 상태는 직전 거래일과 동일하다는 원칙.
  • 라이브 실측과 사용자 수기값(평가손익추이 화면)은 D+2 예수금 인정 여부 차이로 며칠간 1~5%대 갭이 날 수 있음 — 정상 범위, 별도 조치 불필요.

cashflow.csv 항목 분류

  • 원금(principal) 이동으로 취급: 개시잔액 · 외부입금 · 외부출금 · 계좌간이체 → 계좌 원금 기준을 바꿈.
  • 원금 이동 아님, 별도 누계로만 집계: 신용이자 · 강의구독비 · 수수료 · 매도세금 · 배당금 → collect.py의 load_cashflow_totals()가 principal 계산에서 제외하고 cum_interest / cum_course_fees / cum_trade_fees / cum_sec_tax / cum_dividend로 따로 합산한다. (이유: 이미 계좌 잔고 변동에 반영된 비용·수익을 원금에서도 빼면 손익이 이중으로 왜곡됨.)
  • 신용이자 · 수수료 · 매도세금 · 배당금은 사용자 요청으로 일별이 아닌 월말 값만 입력 — 효율성 우선.

daily.csv source 컬럼 표기

  • cache / 실측 없음 = collect.py 라이브 실행 결과
  • backfill(...) = PDF·문서 기반으로 역산/추정한 과거값
  • user(수기 키인·...) = 사용자가 Numbers 템플릿에 직접 입력해 병합한 실측값 — 가장 신뢰도 높음
